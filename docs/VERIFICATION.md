# Sumsub business and beneficial-owner verification

Organization → **Verification** connects the separate organization service to Sumsub KYB/KYC. It creates tenant-bound company applicants, generates short-lived provider-hosted links, fetches company/associated-person review results, receives authenticated invalidation webhooks and keeps encrypted minimal status snapshots. The `/kyb/` sample intake remains local and unsubmitted; it links to the organization flow but never uploads its sample draft.

The connector is implemented, not a completed live onboarding. No Sumsub account, paid configuration, production token or real company/person review was supplied or exercised during development. Local tests inject a provider transport and browser services. Production activation needs the operator's contracted service, approved verification levels, privacy/consent/retention configuration and a reachable HTTPS backend. Configuring `environment: production` is not evidence that an entity has been reviewed.

## Operator setup

1. Configure a **full company KYB** level and a separate individual KYC level in the intended Sumsub environment. Enable company registration/ownership review, relevant identity/screening checks, required UBO collection and ongoing monitoring according to the operator's reviewed policy. A data-only level or manually entered GREEN is not independent proof of those checks. The connector trusts the provider's configured level decisions; it does not audit the provider's legal conclusions.
2. Provision the [organization encryption key file](ORGANIZATION_INVOICES.md#configure-encryption). The same protected key ring encrypts verification snapshots with a separate domain and row-bound authenticated encryption; keys remain outside the DB and its backups.
3. Copy [configuration template](../examples/sumsub-config.template.json) **outside the checkout**, for example `/secure/provider.sumsub-config.json`, replace all placeholders and set mode `0600` with the service UID as owner. Do not paste tokens into Front, public manifests, Git, Docker command arguments or a service log. Secret filenames ending `.sumsub-config.json` are ignored by Git as an additional precaution.
4. Set `CORE_SUMSUB_CONFIG_FILE=/secure/provider.sumsub-config.json` for direct `npm run serve:organizations:compiled`. `CORE_ORGANIZATION_INVOICE_KEYS_FILE`, database, audience and exact frontend origins are also required. Absent configuration leaves the feature disabled; there is no built-in test approval or default secret.
5. For Docker, combine `ops/organizations.compose.yaml`, `ops/organizations.invoices.compose.yaml` and [verification overlay](../ops/organizations.verification.compose.yaml), using `--env-file ops/organizations.env` with owner-only host paths `CORE_ORGANIZATION_INVOICE_KEYS_PATH` and `CORE_SUMSUB_CONFIG_PATH`. Enable the existing HTTPS profile as appropriate. Secret mounts are read-only and host-path creation is disabled. See [hosting](HOSTING.md).
6. Register `https://YOUR_ORGANIZATION_ORIGIN/v1/providers/sumsub/webhook` in Sumsub for company and individual events, with a **separate webhook secret** and `HMAC_SHA256_HEX`. Subscribe to review/status changes, reset, step resets, personal/ownership changes, deactivation, deletion and personal-data deletion. Do not subscribe only to company GREEN events: KYB notifications are per applicant. Apply provider-supported monitoring and test actual delivery before relying on it.
7. Keep the server clock synchronized. Run a sandbox qualification with the configured levels and real callback delivery before enabling a production account. Keep the environment and region explicit; the supported API origins are `https://api.sumsub.com` and `https://api.uae.sumsub.com`. Network origins and returned link hosts cannot be chosen by a browser caller.

`clientId`, company/individual level, environment, region and validity policy form a configuration binding. A changed binding makes earlier cases stale; revoke/start a new case under the new policy. Token/secret rotation with the same provider account does not change this public policy binding. The template's 30-day validity is an operator policy example, not a US/UAE legal period.

## Applicant workflow

- Owner/Admin starts an application with a stable UUID request ID and a declared scope: US, Abu Dhabi ADGM or Abu Dhabi mainland. The acknowledgement confirms authority to start the flow; mandatory provider/privacy consents are collected by the hosted provider, not fabricated by this API. ADGM/mainland classification remains a declaration; the country passed to Sumsub is ARE, not a legal jurisdiction certification.
- A case is created locally before remote creation. Its deterministic opaque `externalUserId` binds the organization and unique case. A lost creation response is recovered by external ID before another create; an uncertain browser action can reload the current application. A current active case cannot be replaced silently. Up to 25 cases are retained per organization; history is not deleted to reset validity.
- **Create secure verification link** looks up/creates the company applicant and returns a ten-minute HTTPS provider link. Creating a link suspends current reliance before network I/O. Company details, registration documents, ownership/control structure and individual identity documents are collected in Sumsub. Link URLs remain browser memory only and are cleared by page-hide, logout, origin/org changes and unmount. A redirect back to Core never approves a case.
- **Refresh provider checks** retrieves the company and linked company/person profiles and their `/status` reviews. The company must bind the expected external ID, client and country. All company/person levels must match configured levels. Nested companies are traversed up to depth three and 20 subjects; linked individuals must finish KYC, and at least one natural-person UBO must be present. Missing IDs, skipped/no-UBO exceptions, cycles, unsupported structures and mismatched levels never infer approval. Exception handling and alternative level mappings require additional reviewed policy.
- Only `completed` plus `GREEN` at every required subject is an approval candidate. `RED/RETRY` and `awaitingUser` become **needs information**. The table identifies company versus individual and the declared provider roles; the hosted link displays the provider's actual requests and accepts supplemental documents. `RED/FINAL` is rejected; a GREEN attached to pending/onHold is not approval.

The connector does not expose provider `clientComment`, names, birth dates, identity numbers, document images or detailed moderation narratives to other organization members. Safe subject references and role/status are returned. Do not infer that an organization member's wallet is the legally authorized company signer from these records.

## Expiry, revocation and freshness

Approval expires no later than the **earliest required subject's provider `reviewDate` plus configured validity days**. Missing/malformed/future review dates block approval. First approval persists the expiry; subsequent GREEN reads can shorten it but never extend it. After expiration, create a new application for a new provider review. Front recomputes expiry and marks an approval stale after five minutes without a successful provider observation; backend GET uses the service clock and identical freshness bounds.

Current read failures, manual refresh start, new hosted-link creation and any authenticated provider event suspend reliance. Webhook payloads are verified against their exact raw bytes using constant-time HMAC comparison, with client/environment binding and rejection of manual test sends or SHA1. Exact payload digests are deduplicated durably. Webhooks invalidate; they never directly grant approval from a payload's GREEN. No browser-paid/verified flag is accepted.

Deletion/deactivation/personal-data-deletion events for mapped subjects permanently revoke that case locally. Owner/Admin can **Revoke verification reliance** independently of provider availability; a prior GREEN or replay cannot reactivate it. This revokes local reliance, not the provider's underlying record or any token/protocol permission. A fresh application gets a new external ID; it does not reuse the closed applicant.

In-flight provider reads use version checks and a webhook watermark. A concurrent local revoke, organization permission loss, callback, session expiry or abort prevents committing a late result. Even an event for a newly linked, not-yet-mapped owner fences an in-flight review. Polling also checks the root ownership links again; this is a bounded provider observation, not an atomic snapshot across the external system.

The compiled service polls up to five due cases every 30 seconds with a per-case 25-second bound and two-minute retry scheduling; failed cases do not continuously monopolize the queue. Freshness is not guaranteed by a stopped/unreachable worker: old observations become stale. Provider HTTP errors are sanitized and leave the case non-valid. The private API retains its 8 KiB JSON limit, origin/auth/current-wallet-key/role controls and deadline; the provider-only callback admits up to 64 KiB, shares peer/concurrency limits and needs HMAC instead of a browser session. Many-subject/slow-provider cases can time out and remain stale; use the background worker or repeat an explicit refresh, never infer approval from timeout.

## Private API and storage

| `/v1/organizations/:org/verification` | Behavior |
| --- | --- |
| `GET /` | Current minimal snapshot/configuration status; Owner/Admin/Auditor |
| `POST /` | `{requestId, jurisdiction, acknowledged: true}`; Owner/Admin |
| `POST /link` | `{version}` → secure hosted link, expiry and case ID; Owner/Admin |
| `POST /refresh` | `{version}` → provider-fetched current company/owner state; Owner/Admin |
| `POST /revoke` | `{version}` → irreversible local case revocation; Owner/Admin |

`verification.read` is granted to Owner/Admin/Auditor. `verification.manage` is granted to Owner/Admin. Operator/Viewer cannot read identity-review records. Every mutation rechecks current authorization; async operations recheck the session and organization role after I/O. `OrganizationVerificationClient` is exported by the Node/browser SDK; credentials are supplied by the existing memory-only `OrganizationClient`.

Three new SQL tables retain encrypted case snapshots, keyed applicant-index hashes and deduplicated event digests. Opaque IDs, organization relationships, timing, dirty/revoked/expiry/retry metadata remain visible to the service. Provider secrets never enter these tables. Raw identity profiles are minimized immediately after each fetch; document contents remain with the provider. Audit entries contain event type/state/counts, not raw provider bodies or secrets. The event digest store is bounded at 50,000 entries; capacity fails closed and needs an explicit retention/rotation policy before larger deployments.

Backups retain the encrypted case history, subject links and deduplication data. **Every restored case is locally revoked**, in addition to the existing access quarantine/session disposal. Historical verification or revocation state cannot be silently reinstated by activating an old backup; an authorized member must start a new case and obtain new provider review. Keep decryption keys separately. See [backup/recovery](ORGANIZATION_BACKUPS.md).

This integration produces no issuer-signed on-chain credential and does not alter the existing `sdk/kyb.ts` attestation verifier. Organization creation/login claims remain false; provider review is a separate explicit record, not a blanket legal-identity claim. It does not add KYB gating or dual authorization to permissionless settlement contracts, confer custody/signing power, withhold tax or file reports.
