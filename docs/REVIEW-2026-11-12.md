# Invoice review and next implementation — 2026-11-12

Scope: invoice terms v1/v2, browser status validation and checkout lifecycle, read-only HTTP error handling, and SQLite reconciliation. This is a focused code review, not an independent contract/circuit security audit. Contract bytecode, proof domains, fees and fixed-destination recovery do not change.

## Findings resolved

| Priority | Finding and impact | Resolution and regression |
| --- | --- | --- |
| P2 | `validateInvoiceStatus` checked aggregate late amount bounds, but not agreement with confirmation flags. A malformed response could set `lateTokens: "0"` and `state: "paid"` while containing a late confirmation. | Recompute late principal from the confirmed flags and fixed denomination; reject contradictory responses. Covers omitted, inflated and changed late flags. |
| P2 | `InvoiceSummary` cleared its own status on failure but left the parent checkout's last accepted status intact. Imports could appear available after a failed refresh; an asynchronous read could also finish after deployment trust changed. Fresh pre-sign checks still limited the original impact. | Clear local and parent status at refresh/invalidation/failure; discard results from older request generations. Browser regressions cover failed reads, recovery after a new successful read and a response arriving after trust invalidation. |
| P2 | Invoice status errors from SQLite bypassed the index error boundary and became `502 CHAIN_READ_FAILED`, unlike other index reads. | Return `503 INDEX_READ_FAILED` for index implementation errors, preserve explicit `IndexError` codes and omit internal database diagnostics. HTTP regression exercises a failing index adapter. |

## Next work completed

V2 invoice lookup previously paged all completed payouts to a recipient and filtered references afterward. Its 1,000-record budget could be exhausted by unrelated history. The SQLite adapter now filters the signed reference set directly through the existing disclosure-root index, retaining the recipient/kind checks, consistent read transaction and upper-bound cursors. Input is strictly 1–32 distinct hex roots, passed as SQL parameters. Public activity inputs remain unchanged. Older adapters retain a conservative bounded fallback.

Regressions reconcile two matching payments behind 1,200 unrelated payouts, exclude later appends from an existing page sequence, reject changed cursor filters and malformed root sets, and report `review_required` when 1,001 matching records exceed the budget. The large histories are synthetic index fixtures, not a claim that current 256-output groups support more spends or that public-network throughput has been measured.

Files: [index store](../sdk/indexer/store.ts), [input schemas](../sdk/indexer/types.ts), [reconciliation](../sdk/invoices.ts), [regression tests](../tests/invoice-privacy.test.ts).

## Remaining boundaries

The index reports observed finalized records, not latest-chain freshness or a Byzantine-provider proof. Per-reference uniqueness and invoice expiry are application checks rather than on-chain reservations. Public recipients, amounts, signers and timing remain visible. Reference-set lookup gives the API the invoice's public reference association, as before; it is not private computation. Large public-network backfills, deployment, real KYB/tax services and production security review remain on the backlog.
